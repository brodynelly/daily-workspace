## Common write contract (if a row is approved)

1. **Human selects owner and exact target.** Show a destination-specific review of the submitted text/change, canonical project/repository or vault-relative path, and the native record ID and observed revision for edits. A default destination must never silently change the owner. Require a fresh explicit confirmation for **each** externally persistent action, including every step of a multi-step Luuna workflow; pressing Capture or accepting a restart draft is not a blanket authorization. On cancel, keep the draft and write nothing.
2. **Use deterministic app code, never a model write tool.** A model may propose text only; the user edits/reviews it in the ordinary capture or action UI. The model cannot invoke a write adapter, select an authoritative owner, confirm an action, or assert a new source status. Read-only Assistant tools, cited observations and the accepted restart-record flow remain unchanged.
3. **Validate before writing.** Resolve vault paths through the live security-scoped bookmark and `NoteVault.resolve`, after the exclusion policy has run; refuse hidden, `_`-prefixed, archive, templates, generated automation, raw ingest, nested-repo and generated-board targets. Refuse an absent/unauthorized/partial owner or changed vault/project/connection rather than treating it as empty or replaying a stale intent. Never create a vault-root fallback or derive a path from model output. Keep keys/tokens only in the Keychain, app-owned metadata in `WorkspaceDirectory`, and content/credentials out of logs.
4. **Report what actually happened.** Keep the draft until the destination confirms a durable result. Distinguish `Draft — not submitted`, `Awaiting confirmation`, `Submitting`, `Saved`/`Captured` (only after a durable `NoteVault` save or a successful `lu` response identifying the native record), `Conflict — review again`, and `Outcome unknown — check owner before retry`. For Luuna, read back the returned ID/revision when needed to establish authoritative state and board visibility; a successful process exit alone without a valid native result does not certify a save. Never label an inaccessible owner `empty`; do not infer ticket closure from a run's `completed` status. A network timeout or interrupted CLI response is not a failure that makes a blind second submission safe.
5. **Handle conflict without data loss.** Every edit uses the observed source snapshot/revision, not an implicit latest value. On conflict, show the owner's new state, retain the draft and require a new review and confirmation. No silent merge, retry, replacement or overwrite. Vault saves retain the six `CONTRIBUTING.md` invariants: exact loaded bytes plus edits, atomic saves with snapshot checks, UTF-8 only, confinement including symlinks, no delete/rename/move, recovery before any discard, and success only after disk save.

## Owner-specific implementation contracts

### A. Org inbox

Use the verified file inside the currently selected vault, not a guessed path or a separately initialized Org store. Preview the exact Org text to append, including any heading/timestamp, and preserve the file's existing bytes, encoding and line endings. Load a snapshot and use the `NoteVault` conflict-checked atomic save; do **not** use an unguarded file append. Emacs may edit this file concurrently: before enabling writes, implement and exercise a coordination strategy that prevents lost Emacs edits across the read/check/replace window (or refuse to write if the strategy cannot be verified). A detected change means conflict and a fresh human review, not automatic re-append. Keep Org's native keyword/status verbatim in subsequent reads; capture does not mark anything `TODO` or `DONE` unless the confirmed entry explicitly contains it. This is an Org inbox entry, not a local task or Luuna ticket.

### B. Vault Quick Notes

Require the user to choose the precise in-vault note path/folder in the review UI; verify the selected existing parent, source scope and allowed file type. For a new note call `NoteVault.create` (refuse if it already exists); for an existing note load its snapshot and save/append only while it still matches. No `overwrite`, root fallback, path traversal, auto-created directory tree, generated file, or rename. If the note is already open with unsaved edits or a conflict in `NoteDocument`, route through that document's save/recovery flow rather than writing behind it. A saved note remains context, not an actionable task inferred from a checkbox. The daily-note resolver continues to use `.obsidian/daily-notes.json` for today's note; Quick Notes is an additional explicit destination, not a replacement for that rule.

### E. Assistant-guided vault note drafts (additional approval required)

Offer a transient draft from a cited conversation: note body, the source paths used, and the text to insert or replace. The user—not the model—chooses the exact existing note or a new path under an existing visible folder, and reviews the full before/after text and destination before each save. A changed file, unsaved editor state or revoked bookmark refuses the save without losing the draft. Use the existing `NoteDocument` conflict/recovery flow when the target is open; otherwise `NoteVault.create` or snapshot-checked atomic save, never an unguarded append. Recheck the exclusion and path-confinement rules before loading and before committing. Link only to source-backed relationships and preserve citations, full-path wikilinks, frontmatter and original line endings. Do not infer tasks from historical checkboxes or change any task owner. AI remains a draft producer with read-only tools; no write occurs until row B **and** this row E have separate, recorded owner approvals.

### C. Luuna through the runtime CLI

Use one allowlisted fixed-argv runner for the verified `~/.local/bin/lu` executable, a safe working directory outside the vault, structured `--json` output, deadlines/process-group termination and bounded output. No shell interpolation, arbitrary user-provided command name, direct `lu missions|atlas|beacon` or runtime initialization. Provide `LUUNA_URL` for the loopback-only verified runtime and `LUUNA_API_TOKEN` from the Keychain only in the child environment; never place secrets in argv, files, stdout/stderr logs, analytics or a persisted job. Distinguish unauthorized, unavailable, stale, refused and unknown-result states, with source identity rechecked before action. Re-read installed command help at implementation/upgrade time; unsupported options must be refused, not guessed.

A `--key` is an idempotency guarantee **only where the installed command exposes it**, not a generic Luuna flag; never apply it to `edit-ticket`, `approve` or `implement`. Persist non-secret operation IDs/keys and their target association in app-owned storage to survive a restart. For operations without a key, an ambiguous outcome must be reconciled against the runtime's native record before any fresh confirmation or retry. CLI replies supply native statuses; the app must not relabel a `completed` run as a closed ticket.

## Automation boundary and audit

Jobs are owned by the app, stored under `~/.config/daily-workspace/` with an explicit enable switch **off by default**, named human owner, action type, destination owner/ID, schedule, permission and last outcome. A scheduled read-only refresh may run when opted in. If a job prepares a write, it must leave an actionable draft for Brody to review and confirm at execution time; missing confirmation, offline status, changed scope/revision or missed schedule means **no write**, never a queued silent replay. Opt-in to scheduling alone does not waive per-write confirmation. Model invocation is not implied by enabling a job; it needs a separate explicit opt-in, remains a draft producer only, and cannot authorize a write. No publishing, plan approval or implementation by timer under this policy.

Append an app-owned audit record per attempted run: job/action ID, configured human owner and destination authority/record ID (vault paths privacy-protected), schedule/trigger, confirmation reference and time, observed revision/hash, submitted command kind (no secret args or text), outcome/returned native ID/revision, and error category. Protect audit data with app-folder permissions; do not log note bodies, prompts, chat, tokens or raw CLI output. A failed, skipped or ambiguous run is visible rather than silently marked done. Deleting/disabling a job prevents future executions but does not erase the audit record. Any unattended write or unattended model call would require a **separate** explicit owner approval defining its exact scopes, limits and audit contract; T00 as proposed does not authorize one.

## Alternatives and approval boundary

- **Keep all external owners read-only** (lowest risk): use `Open source` and manual capture; no A–D approval. Local capture and the restart ledger remain available.
- **Approve only selected destinations**: e.g. Quick Notes but not Org until Emacs concurrency is proven, or tickets but not Luuna plan/approve/implement/publish. Record command-level restrictions; unapproved operations stay unavailable. This is preferable to an all-or-nothing switch when prerequisites differ.
- **Direct HTTP writes or component-store commands** instead of `lu`: rejected for this proposal because they bypass the verified runtime CLI's identity/policy boundary and risk a second local source of truth. A different proposal would be required.
- **Unattended write automation** instead of drafts + per-run confirmation: lower friction but materially different authority and failure modes; **not** part of the requested approval and must be evaluated separately. Likewise, no `tasks.json` migration or assistant write tools are being requested.

**Approval is the dated owner decision recorded in `AGENTS.md`, not a ticket status or Luuna project confirmation.** Only B and E are approved, within their stated restrictions. A, C and D were declined for this app; no Org/Luuna app writes, automation, saved Assistant transcript or `tasks.json` migration is authorized.
